# 测试用例编写标准

## 1. 用例编号规则
### 1.1 编号格式
``{SystemModule}-{Component}-{SEQ}`

### 1.2 字段说明
- `SystemModule`：从系统角度划分的模块，如Trade：交易模块
- `Component`：页面下的某一个区块或者子组件（注意划分的颗粒度），如Filter：筛选组件; SubmitBtn: 提交按钮; SearchInput: 搜索输入框
- `SEQ`：三位数字序号，对于某个组件涉及到多个功能点时，可用序号划分。同一组件下的测试点按发现顺序递增，预留号段：001-099 正常流程，100-199 异常流程，200-299 边界条件，300-399 安全测试


## 2. 标题与结构要求
### 2.1 用例标题
- 用例类型：功能、边界、异常、安全
- 标题必须具体，直接描述验证目标
- 避免使用“测试登录”“验证退款”这类空泛表述
- 推荐格式：`[动作] + [对象] + [条件/场景]`

### 2.2 前置条件
- 只保留当前用例执行所必需的条件
- 使用有序列表描述
- 不要混入测试步骤中的动作

### 2.3 测试步骤
- 每一步只写一个核心动作
- 步骤必须可执行、可复现
- 涉及输入时优先写明确值，不写“合法数据”“非法数据”

### 2.4 预期结果
- 结果必须具体且可验证
- 尽量写清页面反馈、接口返回、状态变化、数据库变化等
- 避免仅写“正常”“成功”“失败”

### 2.5 测试数据
描述测试数据的一些构造步骤方法或存放已有的测试数据
- 优先给具体值与说明
- 数据项需与步骤和预期保持一致
- **严禁**随意编造测试数据，如URL、测试账号等

## 3. 设计原则
- 一条用例只验证一个清晰测试点
- 主流程、异常流、边界流应拆分为独立用例
- 高风险规则优先单独成例，避免与低风险点混合
- 对于可穷举的规则组合，优先使用等价类、边界值、判定表等方法控制数量

## 4. 质量校验清单
- 用例 ID 是否符合规则
- 标题是否清晰、无歧义
- 步骤是否可独立执行
- 预期是否可验证
- 功能点是否可追溯
- 是否存在明显冗余或多目标混测
