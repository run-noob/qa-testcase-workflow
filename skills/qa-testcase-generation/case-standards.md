# 测试用例编写标准

## 1. 模块/子模块划分和命名
### 1.1 划分原则
- 按功能/业务模块
以系统用户可见的功能区域为准，如“用户中心”“订单管理”“支付中心”“搜索服务”等。
- 按页面/界面
如果系统以页面为主，可用页面名作为模块，下分功能点。
推荐方式：一级模块 = 功能域，二级子模块 = 功能点/页面/接口，最多不要超过三级。
- **不是所有需求都要有子模块定义**，仅当模块非常复杂且用例较多的情况下细分子模块

### 1.2 命名规范
- 模块名: 通常为名词或名词短语，如“商品管理”而非“管理商品”。
- 子模块: 可带动作或具体功能，如“添加商品”“商品列表”。
示例结构：
```
模块：用户管理
├── 子模块：注册
├── 子模块：登录
└── 子模块：找回密码

模块：订单中心
├── 子模块：创建订单
├── 子模块：订单列表
└── 子模块：退款申请
```

## 2. 标题与结构要求
### 2.1 用例优先级
- **P0**:
  - 核心冒烟测试用例，适用于核心主链路、阻塞性功能、上线失败会直接影响核心业务可用性的场景。
  - 数量建议：10-20%
- **P1**: 
  - 适用于重要业务分支、关键流程功能点验证、失败后会严重影响用户体验但存在替代路径的场景。
  - 数量建议：30-40%
- **P2**: 
  - 适用于一般功能、常见边界、次要业务分支。
  - 数量建议：30-40%
- **P3**: 
  - 适用于边缘场景、极端条件、低频兼容性或体验细节。
  - 数量建议：< 10%

### 2.2 用例标题
- 用例类型：正常、边界、异常、安全
- 标题必须具体，直接描述测试目标
- 避免使用“测试登录”“验证退款”这类空泛表述
- 推荐格式：`[动作] + [对象] + [条件/场景]`

### 2.3 前置条件
- 只保留当前用例执行所必需的条件
- 使用有序列表描述
- 不要混入测试步骤中的动作

### 2.4 测试步骤
- 每一步只写一个核心动作
- 步骤必须可执行、可复现
- 涉及输入时优先写明确值，不写“合法数据”“非法数据”

### 2.5 预期结果
- 结果必须具体且可验证
- 尽量写清页面反馈、接口返回、状态变化、数据库变化等
- 避免仅写“正常”“成功”“失败”

### 2.6 测试数据
描述测试数据的一些构造步骤方法或存放已有的测试数据
- 优先给具体值与说明
- 数据项需与步骤和预期保持一致
- **严禁**随意编造测试数据，如URL、测试账号等

## 4. 设计原则
- 一条用例只验证一个完整的操作路径或业务流程；切换/往返类操作的正反向属于同一操作路径
- 正常主流程、异常流、边界流应拆分为独立用例
- 高风险规则优先单独成例，避免与低风险点混合
- 对于可穷举的规则组合，优先使用等价类、边界值、判定表等方法控制数量

## 5. 质量校验清单
- 模块划分与命名是否规范
- 标题是否清晰、无歧义
- 步骤是否可独立执行
- 预期是否可验证
- 功能点是否可追溯
- 是否存在明显冗余或多目标混测
